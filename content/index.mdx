<span data-home-page />

Define your HTTP API once as a shared TypeScript contract. Use that same
contract to derive typed server handlers, fetch clients, TanStack Query helpers,
and OpenAPI documents.

`rest-rpc` keeps the wire format REST-shaped while making application code feel
like ordinary function calls.

## One Contract, Many Surfaces

HTTP details live in the contract, then clients and handlers use the route tree
as typed functions.

<Tabs>
<Tab title="Contract">

```ts
export const api = router({
	todos: {
		update: {
			method: "PATCH",
			path: "/todos/:id",
			query: {
				notify: z.coerce.boolean().optional(),
			},
			headers: {
				"x-request-id": z.string().optional(),
			},
			body: {
				title: z.string().min(1),
				completed: z.boolean().optional(),
			},
			response: todoSchema,
		},
	},
});
```

</Tab>
<Tab title="Server">

```ts
const routes = router(api, {
	todos: {
		update({ id, title, completed, notify, "x-request-id": requestId }) {
			return updateTodo({
				id,
				title,
				completed,
				notify,
				requestId,
			});
		},
	},
});
```

</Tab>
<Tab title="Client">

```ts
const todo = await client.todos.update.fetch({
	id: "todo_1",
	title: "Ship the docs",
	completed: true,
	notify: true,
	"x-request-id": "req_123",
});
```

</Tab>
<Tab title="curl">

```bash
curl -X PATCH "https://api.example.com/todos/todo_1?notify=true" \
	-H "content-type: application/json" \
	-H "x-request-id: req_123" \
	-d '{"title":"Ship the docs","completed":true}'
```

</Tab>
</Tabs>

:::tip[Small by design]
`rest-rpc` stays focused on the API boundary so it can fit into code you already
have. You keep using normal HTTP routes, your existing framework, middleware,
authentication, database layer, and deployment model. The contract is just the
shared description of that boundary, which makes adoption incremental and
failures easier to trace back to a method, path, request shape, or response
shape.
:::

## Common Questions

<Accordion>
  <AccordionItem title="Who is rest-rpc for?">
    `rest-rpc` is for developers who want end-to-end type safety and
    RPC-style, function-shaped usage without replacing familiar HTTP concepts.
    You keep methods, paths, headers, bodies, status codes, and your existing
    framework, while the shared contract connects the server and client types in ergonomic way.
  </AccordionItem>
  <AccordionItem title="Do I have to restructure my app?">
    No. Keep your framework, middleware, authentication, database access, and
    deployment model. Add the contract at the API boundary, then adopt the
    server adapters, client, TanStack Query helpers, or OpenAPI generation as
    they become useful.
  </AccordionItem>
  <AccordionItem title="Do I need to learn a new API model?">
    Not really. The contract is still made of HTTP methods, paths, request
    locations, status codes, headers, and response bodies. The generated client
    and handlers make those routes nicer to call from TypeScript, but they do
    not hide what goes over the wire.
  </AccordionItem>
  <AccordionItem title="What happens when something breaks?">
    You debug the same boundary you would debug by hand: method, path, query,
    headers, body, status, and response shape. Because those pieces live in one
    contract, type errors and runtime validation errors point back to the route
    declaration instead of a separate client or server type.
  </AccordionItem>
</Accordion>
