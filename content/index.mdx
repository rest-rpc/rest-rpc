<span data-home-page />

Define REST APIs with methods, paths, request segments, response statuses,
content types, and streaming—or start with sensible defaults. Call them through
a typed client that feels like ordinary function calls.

`rest-rpc` puts HTTP first. Define routes alongside their handlers and infer
client types from their return values. Use your existing server framework,
middleware, and deployment model.

## Use Only the Details You Need

<Tabs>
<Tab title="Routes">

```ts twoslash
// ---cut-start---
// @filename: server.ts
import { route } from "@rest-rpc/express";
import { z } from "zod";

declare function createTodo(title: string): { id: string; title: string };
declare function findTodo(
	id: string,
): { id: string; title: string } | undefined;
// ---cut-end---
// POST /todos/create, flat JSON input, plain result.
const create = route
	.input(z.object({ title: z.string() }))
	.handler(({ input: { title } }) => createTodo(title));

// Explicit method, path, request segments, statuses, and response headers.
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.query(z.object({ uppercase: z.enum(["yes", "no"]).optional() }))
	.headers(z.object({ "x-request-id": z.string().optional() }))
	.handler(({ params, query, headers }) => {
		const todo = findTodo(params.id);
		if (!todo) {
			return { status: 404, body: { code: "TODO_NOT_FOUND" as const } };
		}
		return {
			status: 200,
			responseHeaders: { "x-request-id": headers["x-request-id"] },
			body: {
				...todo,
				title:
					query.uppercase === "yes" ? todo.title.toUpperCase() : todo.title,
			},
		};
	});

export const routes = { todos: { create, get } };
```

// @filename: client.ts
// ---cut-end---
import { initClient } from "@rest-rpc/core";
import { generateContractFromType } from "@rest-rpc/core/generate";
import type { routes } from "./server";

// Run generation at build time for browser clients.
const api = generateContractFromType<typeof routes>({
	filePath: "./server.ts",
	exportName: "routes",
});
const client = initClient(api, { baseUrl: "http://localhost:3000" });

const todo = await client.todos.create({ title: "Write docs" });
const response = await client.todos.get({
	params: { id: todo.id },
	query: { uppercase: "yes" },
	headers: { "x-request-id": "req_1" },
});

if (response.status === 200) {
	console.log(response.body.title);
}
```

// @filename: client-contract.ts
import { generateContractFromType } from "@rest-rpc/core/generate";
import type { routes } from "./server";

export const api = generateContractFromType<typeof routes>({
	filePath: "./server.ts",
	exportName: "routes",
});

// @filename: client.tsx
import { api } from "./client-contract";
// ---cut-end---
import { createTanstackQueryHelpers } from "@rest-rpc/tanstack-query";
import { useQuery, useMutation } from "@tanstack/react-query";

const tq = createTanstackQueryHelpers(api, {
	baseUrl: "http://localhost:3000",
});

const todo = useQuery(
	tq.todos.get.queryOptions({
		params: { id: "todo_1" },
		query: { uppercase: "yes" },
	}),
);
const create = useMutation(tq.todos.create.mutationOptions());

create.mutate({ title: "Write docs" });
```

Plain outputs reach the client as data. Returns with `status` reach it as HTTP
response envelopes. The builder keeps both shapes typed without making you
choose a separate route kind.

:::tip[Small by design]
`rest-rpc` stays focused on the API boundary so it can fit into code you already
have. You keep using normal HTTP routes, your existing framework, middleware,
authentication, database layer, and deployment model. Adopt the route builder,
adapters, client, or OpenAPI generation as they become useful.
:::

## Common Questions

<Accordion>
	<AccordionItem title="Who is rest-rpc for?">
		`rest-rpc` is for developers who want end-to-end type safety and RPC-like
		ergonomics without replacing familiar HTTP concepts. You keep methods,
		paths, headers, bodies, status codes, and your existing framework, while
		route declarations connect server and client types.
	</AccordionItem>
	<AccordionItem title="Do I have to restructure my app?">
		No. Keep your framework, middleware, authentication, database access, and
		deployment model. Add typed routes at the API boundary and adopt the client,
		TanStack Query helpers, or OpenAPI generation as they become useful.
	</AccordionItem>
	<AccordionItem title="Do I need to learn a new API model?">
		The model is ordinary HTTP: methods, paths, request locations, status codes,
		headers, and response bodies. Choose explicit details when you need them or
		use defaults for simple routes.
	</AccordionItem>
	<AccordionItem title="Can I have a separate contract?">
		Yes. Declare the HTTP interface independently, implement it with any server
		adapter, and share it directly with clients. See the [Contract-first
		Quickstart](/docs/contract-first-quickstart/).
	</AccordionItem>
	<AccordionItem title="What happens when something breaks?">
		You debug the same boundary you would debug by hand: method, path, query,
		headers, body, status, and response shape. Because those pieces live in one
		route declaration, type errors and validation errors point back to that
		declaration.
	</AccordionItem>
</Accordion>
