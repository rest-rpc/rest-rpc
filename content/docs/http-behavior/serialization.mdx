---
title: Serialization and Codecs
description: How values are encoded over HTTP and how to customize body codecs.
---

HTTP values travel through URL strings, headers, or request and response bodies.
These rules are shared by the client and every server adapter. See the
[Route Builder](/docs/route-builder) for declaring the interface and
[Schemas and Validation](/docs/http-behavior/schemas) for validation boundaries.

## Path, Query, and Headers

The client stringifies scalar values. The server passes HTTP strings to request
schemas, which perform any required coercion.

| Location    | Client value shape                                   | Wire representation                                        |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| Path params | Object of string, number, or boolean values          | Each value is URL-encoded into its path segment            |
| Query       | Object of scalars, scalar arrays, or optional values | Scalars use `key=value`. Arrays use repeated `key[]=value` |
| Headers     | Object of scalars or optional values                 | String values under lowercase header names                 |

Undefined query and header values are omitted. Missing required path params
fail on the client. Nested query objects are unsupported. A flat GET `.input()`
uses the same query encoding as `.query()`.

The server reconstructs `tag[]=one&tag[]=two` as `{ tag: ["one", "two"] }`.
A single `tag[]=one` remains an array. Repeated scalar keys such as
`tag=one&tag=two` keep the last value.

Declare header schemas with lowercase names. Incoming header names are
normalized to lowercase, so uppercase schema keys do not match them.

## Bodies and Content Types

Body codecs serialize values into HTTP bodies and deserialize HTTP bodies into
values. `.input()`, `.body()`, `.output()`, and `.response()` default to
`application/json`. Specifying the `contentType` option can select another media type.
Schemas operate on values before encoding and after decoding.

Outgoing codecs are selected from the declared content type. Incoming codecs
are selected from the received `Content-Type` header. Matching uses the lowercase
base media type without parameters, so `application/json; charset=utf-8` matches
the JSON codec.

A request whose `Content-Type` is not declared by the route is rejected with
`415` before validation. A client response without a content type or body
decodes to `undefined`.

When a route declares a list of content types, the client selects the request
type with the [`contentType` call option](/docs/client/fetch-client#per-call-options),
and the handler selects the response type with its returned `contentType`. The
schema and codecs must agree on the values represented by each selected type.

## Default Codecs

| Content type                                 | Value                                                  |
| -------------------------------------------- | ------------------------------------------------------ |
| `application/json` or any `+json` media type | JSON value                                             |
| `application/x-www-form-urlencoded`          | `URLSearchParams`                                      |
| `multipart/form-data`                        | `FormData`                                             |
| `text/*`                                     | `string`                                               |
| Any other media type                         | `Blob` or `Uint8Array` when sent, `Blob` when received |

The client uses these codecs for requests and responses. Server adapters
follow the same mapping, with framework-specific differences in which bodies
they parse and which values they can send. See the "Request and Response
Bodies" section of your [server adapter](/docs/server/express#request-and-response-bodies).

## Streams

[Streaming routes](/docs/streaming) respond with `text/event-stream` and do not
use body codecs. Each yielded value is sent as JSON in an SSE `data` field, with
optional `id`, `event`, and `retry` fields.

## Custom Codecs

Create a `BodyCodec` and pass it in `bodyCodecs` to a server adapter or the
client. Each codec has a `match(mediaType)` function and optional `serialize`
and `deserialize` functions. Custom codecs run before the defaults. The first
matching implementation wins independently for each operation, so overriding
only serialization keeps the default deserializer.

<Tabs>
<Tab title="Server Adapter">

```ts
import { createRouteHandler, type BodyCodec } from "@rest-rpc/fetch";
import { routes } from "./routes";

const binaryCodec: BodyCodec<Request> = {
	match: (mediaType) => mediaType === "application/octet-stream",
	serialize: (value) => {
		if (!(value instanceof Uint8Array)) {
			throw new TypeError("Expected Uint8Array body");
		}
		return { body: value };
	},
	deserialize: async (source) => new Uint8Array(await source.arrayBuffer()),
};

const handler = createRouteHandler(routes, {
	bodyCodecs: [binaryCodec],
});
```

</Tab>
<Tab title="Client">

```ts
import { initClient, type BodyCodec } from "@rest-rpc/core";
import { contract } from "./contract";

const binaryCodec: BodyCodec<Response> = {
	match: (mediaType) => mediaType === "application/octet-stream",
	serialize: (value) => {
		if (!(value instanceof Uint8Array)) {
			throw new TypeError("Expected Uint8Array body");
		}
		return { body: value };
	},
	deserialize: async (source) => new Uint8Array(await source.arrayBuffer()),
};

const client = initClient(contract, {
	baseUrl: "https://api.example.com",
	bodyCodecs: [binaryCodec],
});
```

</Tab>
</Tabs>

Use schemas that accept the decoded values, and configure compatible codecs on
both ends.

### Serializer Result

`serialize(value, declaredContentType)` receives the full selected content type,
including parameters, and returns `{ body, headers?, contentType? }`:

- `body` is sent as-is. On the client it must be a Fetch request body. On the
  server it must be a value the adapter can send. See your adapter's
  "Request and Response Bodies" section.
- `headers` adds headers for the serialized body.
- Omitting `contentType` preserves the declared content type. A string may change
  parameters but must keep the same base media type. `null` omits the explicit
  content-type header, allowing Fetch to supply it for bodies such as `FormData`.

### Deserializer Source

`deserialize(source)` returns the value to validate. On the client, `source` is
the Fetch `Response`. On the server, it is the adapter's native request object.

Custom deserializers read the body themselves, so they are responsible for
their own size limits and error handling. Errors they throw are not converted
into responses and propagate to the adapter's normal error handling.
