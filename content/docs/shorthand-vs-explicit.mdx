---
title: Shorthand vs Explicit
description: See how rest-rpc convenience APIs relate to their explicit alternatives.
---

`rest-rpc` starts with a contract. Once the contract declares the HTTP method,
path, request locations, and responses, the library can derive typed clients,
server handlers, OpenAPI output, TanStack Query helpers, and useful call-site
shorthands from that same source of truth.

The docs mostly use the concise defaults because they keep normal routes easy to
read. Those defaults are convenience layers, not lock-in. When explicit HTTP
shape is clearer for a route or codebase, rest-rpc supports that too.

## Request Shape

By default, request fields from `params`, `query`, JSON `body`, and
`headers` are flattened into one request object.

```ts
const api = {
	todos: {
		update: route
			.patch("/todos/:id")
			.params(z.object({ id: z.string() }))
			.query(z.object({ notify: z.boolean().optional() }))
			.body(z.object({ title: z.string() }))
			.headers(z.object({ "x-request-id": z.string() }))
			.response(200, todoSchema),
	},
};
```

```ts
await client.todos.update.fetch({
	id: "todo_1",
	notify: true,
	title: "Write docs",
	"x-request-id": "req_1",
});
```

Use `flattenRequestKeys: false` when you want the call site to keep the HTTP
request locations visible.

```ts
const groupedRoute = route.with({ flattenRequestKeys: false });

const api = {
	todos: {
		update: groupedRoute
			.patch("/todos/:id")
			.params(z.object({ id: z.string() }))
			.query(z.object({ notify: z.boolean().optional() }))
			.body(z.object({ title: z.string() }))
			.headers(z.object({ "x-request-id": z.string() }))
			.response(200, todoSchema),
	},
};
```

```ts
await client.todos.update.fetch({
	params: { id: "todo_1" },
	query: { notify: true },
	body: { title: "Write docs" },
	headers: { "x-request-id": "req_1" },
});
```

Server handlers mirror the request shape the client uses.

```ts
// Flattened request keys
update({ id, notify, title, "x-request-id": requestId }) {
	return updateTodo({ id, notify, title, requestId });
}
```

```ts
// Explicit request segments
update({ params, query, body, headers }) {
	return updateTodo({
		id: params.id,
		notify: query.notify,
		title: body.title,
		requestId: headers["x-request-id"],
	});
}
```

Configured route factories are local values, so one contract can use different
defaults for different routes.

```ts
const groupedRoute = route.with({ flattenRequestKeys: false });

const api = {
	todos: {
		update: groupedRoute
			.patch("/todos/:id")
			.params(z.object({ id: z.string() }))
			.body(z.object({ title: z.string() }))
			.response(200, todoSchema),
		batchCreate: route
			.post("/todos/batch")
			.body(z.array(z.object({ title: z.string() })))
			.response(201, z.array(todoSchema)),
	},
};
```

```ts
await client.todos.batchCreate.fetch({
	body: [{ title: "Write docs" }, { title: "Ship the docs" }],
});
```

## Path Params

Declare dynamic path segments with `.params()` so their schema and input type
stay explicit.

```ts
get: route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(200, todoSchema),
```

```ts
await client.todos.get.fetch({ id: "todo_1" });
```

The schema can validate or transform the transport string when the handler
needs a more specific value.

```ts
get: route
	.get("/todos/:id")
	.params(z.object({ id: z.coerce.number<number>().int().positive() }))
	.response(200, todoSchema),
```

## Shared Route Options

Use `route.with()` when many routes share the same contract details. It returns
a configured route factory without changing the default `route` factory.

```ts
const apiRoute = route.with({
	pathPrefix: "/api",
	headers: z.object({
		"x-request-id": z.string().optional(),
	}),
	responses: {
		401: z.object({ code: z.literal("UNAUTHORIZED") }),
	},
});

const api = {
	todos: {
		get: apiRoute
			.get("/todos/:id")
			.params(z.object({ id: z.string() }))
			.response(200, todoSchema),
	},
};
```

Declare the same fields on a route when only that route needs them.

```ts
get: route
	.get("/api/todos/:id")
	.params(z.object({ id: z.string() }))
	.headers(z.object({ "x-request-id": z.string().optional() }))
	.response(200, todoSchema)
	.response(401, z.object({ code: z.literal("UNAUTHORIZED") })),
```

## Custom Bodies

Custom content types stay explicit even when request keys are flattened. The
contract needs to know the full body payload and content type boundary.

```ts
csv: route
	.post("/imports.csv")
	.customBody({
		contentType: "text/csv",
		schema: z.string(),
	})
	.response(201, z.object({ imported: z.number() })),
```

```ts
await client.imports.csv.fetch({
	body: "id,title\n1,Write docs\n",
});
```

For multiple content types, `body` contains the chosen content type and payload.

```ts
await client.images.upload.fetch({
	body: {
		contentType: "image/png",
		payload: bytes,
	},
});
```

## JSON Query

Normal object query params flatten by default.

```ts
await client.todos.list.fetch({
	status: "open",
	limit: 50,
});
```

`.jsonQuery()` is intentionally explicit because the whole JSON value is
transported as one query parameter named `query`.

```ts
search: route
	.get("/search")
	.jsonQuery(
		z.object({
			page: z.number(),
			filters: z.object({ tags: z.array(z.string()) }),
		}),
	)
	.response(200, searchResultsSchema),
```

```ts
await client.search.fetch({
	query: {
		page: 2,
		filters: { tags: ["docs"] },
	},
});
```

With grouped request segments, the JSON query value lives directly under the
`query` segment rather than under `query.query`.

```ts
await client.search.fetch({
	query: {
		page: 2,
		filters: { tags: ["docs"] },
	},
});
```

## Response Declarations

Call `.response(status, schema)` for every response body the route declares.

```ts
create: route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.response(201, todoSchema),
```

The explicit status stays visible beside its schema. Chain another `.response()`
when the status union is part of the contract.

```ts
get: route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(200, todoSchema)
	.response(404, z.object({ code: z.literal("TODO_NOT_FOUND") })),
```

Call `.response(status)` without a schema to declare a response without a body.

```ts
remove: route
	.delete("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(204),
```

## Handler Returns

For a route with one successful response, a handler can return the body directly.

```ts
create({ title }) {
	return createTodo({ title });
}
```

Return an explicit response object when the handler chooses a status or when
explicitness is clearer.

```ts
create({ title }) {
	const todo = createTodo({ title });

	return {
		status: 201,
		body: todo,
	};
}
```

## Client Responses

Use `fetch()` when a successful response body is the normal result and
non-success statuses should go through the error path.

```ts
const todo = await client.todos.get.fetch({ id: "todo_1" });
```

Use `fetchResponse()` when HTTP status is normal control flow.

```ts
const response = await client.todos.get.fetchResponse({ id: "todo_1" });

if (response.declared && response.status === 200) {
	response.body.title;
}

if (response.declared && response.status === 404) {
	response.body.code;
}
```

Use `strictStatusCodes: true` when undeclared statuses should throw instead of
being returned as `{ declared: false }`. Then `fetchResponse()` narrows to the
declared status union and you can switch on `status` directly.

```ts
const client = initClient(api, {
	baseUrl: "https://api.example.com",
	strictStatusCodes: true,
});

const response = await client.todos.get.fetchResponse({ id: "todo_1" });

if (response.status === 200) {
	response.body.title;
}

if (response.status === 404) {
	response.body.code;
}
```

## Empty Bodies

Omitting a body setter declares a request without a body.

```ts
list: route.get("/todos").response(200, z.array(todoSchema)),
```

For a no-body request, do not call a body setter. The response status remains
explicit.

```ts
remove: route
	.delete("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(204),
```

## Headers

Pass declared request headers at the call site when they are route-specific.

```ts
await client.todos.list.fetch({
	authorization: "Bearer token",
});
```

Use `getGlobalHeaders` when the client should attach shared headers to every
request. Matching declared request headers become optional at individual call
sites.

```ts
const client = initClient(api, {
	baseUrl: "https://api.example.com",
	getGlobalHeaders: () => ({
		authorization: `Bearer ${readToken()}`,
	}),
});

await client.todos.list.fetch({});
```

## TanStack Query

TanStack Query helpers derive options and keys from the route.

```tsx
const todo = useQuery(
	tq.todos.get.queryOptions({
		id: "todo_1",
	}),
);

const key = tq.todos.get.getKey({ id: "todo_1" });
```

The same query can be written with TanStack Query primitives and the fetch
client directly. This is more explicit, but you have to provide the query key,
forward cancellation, and decide how non-success responses enter TanStack
Query's error channel.

```tsx
import { initClient } from "@rest-rpc/core";
import { queryOptions, useQuery } from "@tanstack/react-query";

const client = initClient(api, {
	baseUrl: "https://api.example.com",
});

const todo = useQuery(
	queryOptions({
		queryKey: ["todos", "get", { id: "todo_1" }],
		async queryFn({ signal }) {
			const response = await client.todos.get.fetchResponse(
				{ id: "todo_1" },
				{ signal },
			);

			if (response.declared && response.status === 200) {
				return {
					status: response.status,
					body: response.body,
					headers: response.headers,
				};
			}

			throw response;
		},
	}),
);
```

For request-based queries, pass a falsy request value to disable the query
function without importing TanStack Query's `skipToken`.

```tsx
const todo = useQuery(
	tq.todos.get.queryOptions(selectedId && { id: selectedId }),
);
```

Use `skipToken` when you prefer the explicit TanStack Query primitive.

```tsx
import { skipToken } from "@tanstack/query-core";

const todo = useQuery(
	tq.todos.get.queryOptions(selectedId ? { id: selectedId } : skipToken),
);
```

Pass normal TanStack Query options when a query needs explicit behavior.

```tsx
const todo = useQuery(
	tq.todos.get.queryOptions(
		{ id: "todo_1" },
		{
			enabled: isReady,
			queryKey: ["todos", "detail", "todo_1"],
			select: (response) => response.body,
		},
	),
);
```

For infinite queries, rest-rpc names the request callbacks after the route
request they carry, while still mapping to TanStack Query's page params.

```tsx
const todos = useInfiniteQuery(
	tq.todos.page.infiniteQueryOptions({
		initialRequest: {
			status: "open",
			limit: 50,
		},
		getNextRequest(lastPage, _allPages, lastRequest) {
			return lastPage.body.nextCursor
				? { ...lastRequest, cursor: lastPage.body.nextCursor }
				: undefined;
		},
	}),
);
```

The same query can be written with TanStack Query primitives and the fetch
client directly. This is more explicit, but you have to provide the query key,
map request values to page params, forward cancellation, and decide how
non-success responses enter TanStack Query's error channel.

```tsx
import { initClient } from "@rest-rpc/core";
import { infiniteQueryOptions, useInfiniteQuery } from "@tanstack/react-query";

const client = initClient(api, {
	baseUrl: "https://api.example.com",
});

const todos = useInfiniteQuery(
	infiniteQueryOptions({
		queryKey: ["todos", "page"],
		initialPageParam: {
			status: "open",
			limit: 50,
		},
		getNextPageParam(lastPage, _allPages, lastRequest) {
			return lastPage.body.nextCursor
				? { ...lastRequest, cursor: lastPage.body.nextCursor }
				: undefined;
		},
		async queryFn({ pageParam, signal }) {
			const response = await client.todos.page.fetchResponse(pageParam, {
				signal,
			});

			if (response.declared && response.status === 200) {
				return {
					status: response.status,
					body: response.body,
					headers: response.headers,
				};
			}

			throw response;
		},
	}),
);
```

## WebSocket Messages

WebSocket message declarations use a fixed `type` discriminator and wrap each
payload in a `message` field.

```ts
chat: route
	.ws("/rooms/:roomId")
	.params(z.object({ roomId: z.string() }))
	.clientMessage("typing", z.object({ roomId: z.string() }))
	.clientMessage("send", z.object({ text: z.string().min(1) }))
	.serverMessage("connected", z.object({ connected: z.boolean() })),
```

```ts
socket.send({
	type: "send",
	message: { text: "Hello from rest-rpc" },
});
```

Add each message type with `.clientMessage()` or `.serverMessage()`. The builder
keeps the direction visible and rejects duplicate message types.

```ts
chat: route
	.ws("/rooms/:roomId")
	.params(z.object({ roomId: z.string() }))
	.clientMessage("typing", z.object({ roomId: z.string() }))
	.clientMessage("send", z.object({ text: z.string().min(1) }))
	.serverMessage("connected", z.object({ memberCount: z.number() }))
	.serverMessage(
		"message",
		z.object({
			text: z.string(),
			sentAt: z.string(),
		}),
	),
```

```ts
socket.send({
	type: "send",
	message: {
		text: "Hello from rest-rpc",
	},
});
```
