---
title: Route Builder
description: Define HTTP routes with default or explicit details, typed results, and streams.
---

A route builder describes an HTTP interface. Start with inputs and plain
results, then choose the HTTP details each route needs. Method and path, input
form, and output form are independent choices.

Import `route` from your server adapter. Attach a handler with `.handler()`;
its return value determines the client's result type.

Schemas can come from Zod, Valibot, ArkType, or another Standard Schema library.
The built-in `type<T>()` utility declares types without runtime validation. See
[Schemas and Validation](/docs/http-behavior/schemas).

## Start with Defaults

```ts
import { route } from "@rest-rpc/express";
import { z } from "zod";

const create = route
	.input(z.object({ title: z.string() }))
	.handler(({ input: { title } }) => ({ id: crypto.randomUUID(), title }));

export const routes = { todos: { create } };
```

Without a method setter, a route uses POST and derives its path from its tree
keys: this route is `POST /todos/create`. The handler receives the JSON body as
`input`, and a plain output uses status 200.

Route trees are plain TypeScript objects. Group routes into modules and compose
them where they are registered or used to create a client.

## Choose a Method and Path

Explicit methods work with the same input and plain result:

```ts
const search = route
	.get("/todos/search")
	.input(z.object({ term: z.string() }))
	.handler(({ input: { term } }) => searchTodos(term));

const todo = route
	.post("/todos")
	.input(z.object({ title: z.string() }))
	.handler(({ input: { title } }) => createTodo(title));
```

Use `.get(path)`, `.post(path)`, `.put(path)`, `.patch(path)`, or `.delete(path)`.
A method can be selected once per route. For GET requests, `.input()` is sent
as query parameters, while other methods send it as the body.

Paths can contain dynamic segments using either `:id` or `{id}` syntax. Declare
each dynamic segment in `.params()`.

The path can also be omitted, in which case the route keeps deriving its path
from its tree keys but uses the specified method instead of the default POST.

```ts
const getRoute = route.get();

const listTodos = getRoute.handler(() => listTodos());
const listNotes = getRoute.handler(() => listNotes());
```

## Declare Request Segments

Use `.params()`, `.query()`, `.headers()`, and `.body()` instead of `.input()`
to read each HTTP request location separately.

```ts
const update = route
	.patch("/todos/:id")
	.params(z.object({ id: z.string() }))
	.query(z.object({ notify: z.enum(["yes", "no"]).optional() }))
	.headers(z.object({ "x-request-id": z.string().optional() }))
	.body(z.object({ title: z.string() }))
	.handler(({ params, query, headers, body }) =>
		updateTodo(params.id, body.title, {
			notify: query.notify === "yes",
			requestId: headers["x-request-id"],
		}),
	);
```

The following rules apply to request segments:

- `.params()` must correspond to dynamic path segments.
- `.body()` is not allowed on GET routes and throws when declared.
- `.input()` cannot be combined with `.params()`, `.query()`, or `.body()`.
  It can be combined with `.headers()`.
- `.input()` requires a static path, because it has no `params` location.

Header schemas must use lowercase names. See
[Serialization and Codecs](/docs/http-behavior/serialization#path-query-and-headers)
for how each location is encoded.

### Combine Input and Headers

`.headers()` can be added to a route that uses `.input()`. The handler receives
both `input` and `headers`:

```ts
const create = route
	.headers(z.object({ authorization: z.string() }))
	.input(z.object({ title: z.string() }))
	.handler(({ input: { title }, headers }) =>
		createTodo(title, headers.authorization),
	);
```

A flat-input client call only accepts the input, so the Fetch client supplies
these headers through [`globalHeaders`](/docs/client/fetch-client#global-headers).

## Stacking Schemas

Stacking schemas is supported for `body`, `query`, `params`, `headers` and `input`. Each schema is validated in declaration order
against the original request value. The schema outputs are shallow-merged into a single object.

:::warning
When stacking schemas, the output of each schema must be an object. Non-object outputs will throw a runtime error
during validation. Use single schema validation for non-object outputs. Avoid using strict schemas such as `z.strictObject()`
that forbid unknown keys, if those keys are required by the other schemas in the stack.
:::

```ts
const stacked = route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.body(z.object({ description: z.string().optional() }))
	.handler(({ body }) => createTodo(body.title, body.description));
```

## Choose Plain Outputs or Status Responses

A plain handler result reaches the client directly. Declare `.output(schema)`
when you want an explicit output schema and runtime validation:

```ts
const create = route
	.input(z.object({ title: z.string() }))
	.output(todoSchema)
	.handler(({ input: { title } }) => createTodo(title));
```

Return `{ status, body }` when the client needs to distinguish HTTP outcomes.
The returned statuses and body types become the client's result type:

```ts
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.handler(({ params }) => {
		const todo = findTodo(params.id);
		return todo
			? { status: 200, body: todo }
			: { status: 404, body: { code: "TODO_NOT_FOUND" as const } };
	});
```

Use `.response()` for each status when you want explicit response schemas.
A route uses either plain outputs or status responses, not both, and each status
can be declared once. A handler returning a status that is not declared fails at
runtime.

```ts
const get = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(200, todoSchema)
	.response(404, z.object({ code: z.literal("TODO_NOT_FOUND") }))
	.handler(({ params }) => {
		const todo = findTodo(params.id);
		return todo
			? { status: 200, body: todo }
			: { status: 404, body: { code: "TODO_NOT_FOUND" } };
	});
```

Omit the schema for a bodyless response, such as `.response(204)`. Declare
status-specific response headers in the options and return them as
`responseHeaders`:

```ts
route
	.post("/todos")
	.body(z.object({ title: z.string() }))
	.response(201, todoSchema, {
		headers: z.object({ location: z.string() }),
	})
	.handler(({ body }) => {
		const todo = createTodo(body.title);
		return {
			status: 201,
			body: todo,
			responseHeaders: { location: `/todos/${todo.id}` },
		};
	});
```

## Declare Content Types

Bodies default to JSON. Use `contentType` on `.input()`, `.body()`, `.output()`,
or `.response()` for text, forms, or binary values.

```ts
const report = route
	.get("/todos/report")
	.output(z.string(), { contentType: "text/plain" })
	.handler(() => ({ contentType: "text/plain", data: createTodoReport() }));
```

A custom-content plain output handler returns `{ contentType, data }` and the
client receives the decoded data. A status response handler uses
`{ status, body, contentType }`. With no output declaration, the adapter can
infer a custom-content output from `{ contentType: "text/plain" as const, data }`.

Content types can also be declared as a list of alternatives. The handler
selects a response content type with its returned `contentType`, and the client
selects a request content type in its
[per-call options](/docs/client/fetch-client#per-call-options). See
[Serialization and Codecs](/docs/http-behavior/serialization) for decoded value
types and compatible codecs.

## Return Streams

Returning an async iterable infers a plain stream. Use `.streamOutput()` for an
explicit data schema or `.streamResponse()` for a status response stream.

```ts
const events = route
	.get("/todos/events")
	.streamOutput(z.object({ id: z.string(), message: z.string() }))
	.handler(() => streamTodoEvents());
```

See [Streaming](/docs/streaming) for handlers, event metadata, validation, and
resuming streams.

## Add Metadata and OpenAPI Details

`.metadata()` attaches application information. `.openAPI()` describes the
operation for OpenAPI generation.

```ts
const list = route
	.get("/todos")
	.metadata({ auth: "required" })
	.openAPI({ summary: "List todos", tags: ["Todos"] })
	.output(z.array(todoSchema))
	.handler(() => listTodos());
```

Both can be called more than once. Metadata objects are shallow-merged, and
OpenAPI details are merged with tags combined. Read metadata from the handler's
`route` argument, middleware, or adapter hooks. See [OpenAPI](/docs/openapi)
for document generation.

## Reuse Builders

Every builder method returns a new route value, so a partially built route can
be shared as a base for other routes without affecting them:

```ts
const authenticated = route
	.headers(z.object({ authorization: z.string() }))
	.metadata({ auth: "required" });

const list = authenticated.get("/todos").handler(() => listTodos());
const remove = authenticated
	.delete("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(204)
	.handler(({ params }) => {
		deleteTodo(params.id);
		return { status: 204 };
	});
```

A route cannot be changed after `.handler()` is attached.

## Handler Arguments

A handler receives one object containing:

- The validated request: `input`, or `params`, `query`, `headers`, and `body`.
- `context`: the per-request [context](/docs/context) shared with middleware.
- `route`: the route declaration, including its method, path, and `metadata`.
- `contentType`: the received request media type, if any.
- `lastEventId`: the `Last-Event-ID` request header, used to [resume streams](/docs/streaming#resume-a-stream).
- `signal`: an `AbortSignal` that aborts when the client disconnects.
- Native framework values such as the request object. See the
  "Framework Context" section of your [server adapter](/docs/server/express#framework-context).

## Type Helpers

Use the type helpers to reuse a route's types in code that lives outside the
route, such as service functions or separately written handlers. For
client-side types, see
[Fetch Client](/docs/client/fetch-client#type-helpers).

Infer from a route declared without `.handler()`, or from a contract route. A
type inferred from a completed route cannot be used inside that route's own
handler, because the route's type depends on the handler.

Each helper also accepts a route tree and infers a matching tree of types.
Declare one type for your routes and index into it where a route's type is
needed:

```ts
import type { InferServerRequest } from "@rest-rpc/express";
import type { routes } from "./routes";

export type ServerRequests = InferServerRequest<typeof routes>;

type CreateTodoRequest = ServerRequests["todos"]["create"];
```

### Infer Server Request

`InferServerRequest` is the validated request a handler receives, without
framework values or context. Use it to pass validated input to code that does
not depend on the server framework.

```ts twoslash
import type { InferServerRequest } from "@rest-rpc/express";
import { route } from "@rest-rpc/express";
import z from "zod";

const updateDeclaration = route
	.patch("/todos/:id")
	.params(z.object({ id: z.string() }))
	.body(z.object({ title: z.string() }));

type UpdateTodoRequest = InferServerRequest<typeof updateDeclaration>;

const updateTodo = ({ params, body }: UpdateTodoRequest) => ({
	id: params.id,
	title: body.title,
});

const update = updateDeclaration.handler(updateTodo);
```

### Infer Server Response

`InferServerResponse` is the value a handler must return for the responses
declared with `.output()` or `.response()`. When responses are inferred from
the handler, there is no declared response to infer before `.handler()`.

```ts twoslash
import type { InferServerResponse } from "@rest-rpc/express";
import { route } from "@rest-rpc/express";
import z from "zod";

const todoSchema = z.object({ id: z.string(), title: z.string() });

const getDeclaration = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(200, todoSchema)
	.response(404, z.object({ code: z.literal("TODO_NOT_FOUND") }));

type GetTodoResponse = InferServerResponse<typeof getDeclaration>;

const findTodo = (id: string): GetTodoResponse =>
	id === "todo_1"
		? { status: 200, body: { id, title: "Write docs" } }
		: { status: 404, body: { code: "TODO_NOT_FOUND" } };

const get = getDeclaration.handler(({ params }) => findTodo(params.id));
```

### Infer Server Handler

`InferServerHandler` is the full handler signature, including framework values
and context. It is exported by each server adapter. Use it to write a handler
separately from its declaration:

```ts twoslash
import { route, type InferServerHandler } from "@rest-rpc/express";
import z from "zod";

const todoSchema = z.object({ id: z.string(), title: z.string() });

const getDeclaration = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.response(200, todoSchema)
	.response(404, z.object({ code: z.literal("TODO_NOT_FOUND") }));

const getTodo: InferServerHandler<typeof getDeclaration> = ({ params, req }) =>
	params.id === "todo_1"
		? { status: 200, body: { id: params.id, title: req.hostname } }
		: { status: 404, body: { code: "TODO_NOT_FOUND" } };

const get = getDeclaration.handler(getTodo);
```
