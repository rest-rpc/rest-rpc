title: Server Adapter Design
description: Understand the boundary between server adapters and @rest-rpc/server
---

Most applications should use a first-party adapter directly. This page explains
the boundary between those adapters and `@rest-rpc/server`, including the
catch-all dispatch model now shared by the Fetch and Node.js adapters.

## Adapter boundary

`@rest-rpc/server` owns transport-independent work:

- typed contract-first implementations and server-first implementation trees
- route matching and specificity ordering
- request validation and flattening
- handler execution, error hooks, and response normalization
- normalized response writing and server-first response-kind metadata
- shared WebSocket validation and message helpers

An adapter owns its transport or framework boundary:

- reading method, path, headers, query, params, and body data
- constructing framework/application context and an abort signal
- registering routes or dispatching a catch-all request
- writing empty, JSON, custom, streaming, and SSE responses
- connecting middleware and runtime-specific WebSocket upgrades

Applications import `route`, `router`, `implement`, and registration/handler
functions from their adapter. Adapter implementations import the lower-level
primitives from `@rest-rpc/server`.

## Two API sources of truth

The framework boundary and the API-definition style are separate choices.

| Style          | Definition                                                                                               | Supported first-party adapters                 |
| -------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Contract-first | A shared contract is implemented with `router(...)`, `route(...)`, or `implement(...)`                   | Express, Fastify, Hono, NestJS, Fetch, Node.js |
| Server-first   | Adapter `route` builders end with `.handler(...)`; client responses can be inferred from handler returns | Fetch, Node.js                                 |

Express, Fastify, Hono, and NestJS intentionally remain contract-first. Their
adapters preserve framework route registration, middleware, dependency
injection, and WebSocket conventions. Fetch and Node.js expose general catch-all
handlers, so the same dispatcher can accept either contract-first or
server-first implementation trees.

## Integration shapes

### Route registration

Express, Fastify, and Hono register each implementation with the framework.
They flatten and split the implementation tree once, then let the framework
perform matching:

```ts
splitRouteImplementations(implementations, {
	handleHttpRoutes(httpRoutes) {
		registerFrameworkHttpRoutes(app, httpRoutes, options);
	},
	handleWebSocketRoutes(webSocketRoutes) {
		registerFrameworkWebSocketRoutes(app, webSocketRoutes, options);
	},
});
```

Inside a registered framework handler, the adapter translates the request and
delegates execution:

```ts
const result = await handleHttpRoute(route, implementation.handler, {
	request: {
		body: req.body,
		query: req.query,
		params: req.params,
		headers: req.headers,
	},
	context: { req, signal },
	errorHandlers,
});

return handleHttpRouteResult(result, frameworkWriter(res));
```

The framework owns routing. `handleHttpRoute` owns validation, invocation, and
normalization; `handleHttpRouteResult` maps the normalized result to the
framework response API.

### Decorator registration

NestJS also lets its router own matching, but discovers routes through
controller metadata rather than a mutable router. The Nest adapter synthesizes
one controller method for each contract route, stores the route declaration as
metadata, and resolves the corresponding implementation when its interceptor
runs.

That bridge keeps Nest modules, controllers, providers, and dependency
injection authoritative while still passing the request through
`handleHttpRoute` and `handleHttpRouteResult`.

### Catch-all dispatch

Fetch and Node.js receive all candidate requests through one handler. Both use
`createHttpDispatcher` to compile an implementation tree into a method/path
matcher:

```ts
const dispatch = createHttpDispatcher(implementations);

const result = await dispatch({
	method,
	path,
	context,
	signal,
	catchParsingErrors: usesDefaultParser,
	errorHandlers,
	decode: async ({ implementation, params }) => ({
		params,
		query: readQuery(),
		headers: readHeaders(),
		body: await parseBody(implementation.route),
	}),
});
```

The `decode` callback runs only after a route matches. This matters for catch-all
handlers: unrelated requests are left untouched, and their bodies are not read.
An `undefined` result means no HTTP/SSE implementation matched.

`@rest-rpc/fetch` converts a matched result with `createFetchResponse` and
returns `{ matched, response }`. `@rest-rpc/node` writes it with
`writeNodeResponse` and returns `{ matched }`, leaving unmatched
`IncomingMessage`/`ServerResponse` pairs untouched for the next middleware or a
404 fallback.

## Response protocol

`handleHttpRoute` normalizes all HTTP results into `empty`, `json`, `custom`, or
`stream` variants. Declared contract responses are validated against their
schemas. A server-first route with no declared responses instead classifies its
handler envelope from `status`, `body`, and optional `contentType`.

Always write normalized results through `handleHttpRouteResult`,
`createFetchResponse`, or `writeNodeResponse`. Besides handling headers and body
kinds consistently, these writers emit the versioned
`X-Rest-Rpc-Response-Kind` metadata required by the server-first `initClient`
overload.
Framework-generated validation/error responses opt out of that metadata, so a
server-first client fails clearly instead of decoding an unexpected body as a
declared route response.

## First-party adapter roles

- Express and Fastify register HTTP and WebSocket routes and expose native
  middleware hooks.
- Hono registers routes on a `Hono` instance and preserves its typed `Context`
  and environment model.
- NestJS maps contracts to controller metadata and runs implementations through
  its interceptor/module lifecycle.
- Fetch dispatches `Request` values and returns standard `Response` values. It
  supports contract-first and server-first HTTP/SSE trees.
- Node.js dispatches `IncomingMessage` values and writes `ServerResponse`
  values. It supports the same contract-first and server-first HTTP/SSE trees
  and can sit behind plain Node HTTP, Express, Koa, or similar middleware stacks.

## WebSocket boundary

WebSocket upgrades and socket lifecycles are more runtime-specific than HTTP.
Express uses a Node HTTP upgrade with `ws`, Fastify uses
`@fastify/websocket`, and Hono uses its framework upgrade API. Their adapters
translate the runtime socket to `WebSocketLike`, call
`prepareWebSocketUpgrade` before acceptance, and call `handleWebSocketRoute`
after the runtime provides the accepted socket.

The general Fetch and Node.js catch-all handlers handle HTTP and SSE routes, not
WebSocket implementations. A custom runtime adapter can add WebSockets with the
shared primitives, but it must own the runtime-specific upgrade and lifecycle
work.
