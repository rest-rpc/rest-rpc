---
title: Building Server Adapters
description: Build registration or catch-all adapters with the current @rest-rpc/server primitives
---

Use a first-party adapter whenever one matches your runtime. Build an adapter
when a framework needs native request/context integration that cannot be
expressed cleanly with `@rest-rpc/fetch` or `@rest-rpc/node`.

This guide shows the current extension points. All shared server APIs are
exported from the `@rest-rpc/server` package root; there are no Fetch or Node
subpath adapters under that package.

## Choose an adapter shape

Use a registration adapter when the framework exposes a router and should own
method/path matching. Use a dispatch adapter when the runtime sends requests to
one catch-all function.

| Shape                  | First-party references | Shared entry points                                                     |
| ---------------------- | ---------------------- | ----------------------------------------------------------------------- |
| Route registration     | Express, Fastify, Hono | `splitRouteImplementations`, `handleHttpRoute`, `handleHttpRouteResult` |
| Decorator registration | NestJS                 | `handleHttpRoute`, `handleHttpRouteResult` plus framework metadata      |
| Catch-all dispatch     | Fetch, Node.js         | `createHttpDispatcher`, response writer helpers                         |

## Expose implementation builders

Framework registration adapters normally expose contract-first `route` and
`router` wrappers typed with their framework context. See the Express, Fastify,
or Hono package entry points for the complete pattern.

A catch-all adapter can support both API styles. Re-export a server-first route
factory bound to the adapter's default context, and wrap `implement` so an
existing contract gets the same context:

```ts
import {
	implement as serverImplement,
	serverFirstRoute,
	type ImplementationBuildersFor,
	type ServerContract,
	type ServerRouteFactory,
} from "@rest-rpc/server";

export interface DefaultContext {}

export const route = serverFirstRoute as ServerRouteFactory<
	{ flattenRequestKeys: true },
	DefaultContext
>;

export function implement<const TNode extends ServerContract>(contract: TNode) {
	return serverImplement(contract) as ImplementationBuildersFor<
		TNode,
		DefaultContext
	>;
}
```

Users can augment `DefaultContext`, build a server-first route ending in
`.handler(...)`, or attach handlers to a contract with `implement(contract)`.
Both produce an ordinary nested implementation tree accepted by shared
dispatch.

## Registration adapters

### Splitting implementations

`splitRouteImplementations` flattens a contract-first implementation tree,
orders routes by specificity, and separates HTTP/SSE implementations from
WebSocket implementations:

```ts
import { splitRouteImplementations } from "@rest-rpc/server";

export function registerRoutes(app, implementations, options = {}) {
	return splitRouteImplementations(implementations, {
		handleHttpRoutes: (routes) =>
			registerFrameworkHttpRoutes(app, routes, options),
		handleWebSocketRoutes: (routes) =>
			registerFrameworkWebSocketRoutes(app, routes, options),
	});
}
```

There is no shared `registerRoutes` function: registration is framework-owned.
The shared helper only prepares the two route lists.

### Registering HTTP routes

For each implementation, translate framework values into four request segments
and construct a context containing an `AbortSignal`:

```ts
import { handleHttpRoute } from "@rest-rpc/server";

const result = await handleHttpRoute(
	implementation.route,
	implementation.handler,
	{
		request: {
			body: readBody(req),
			query: readQuery(req),
			params: readParams(req),
			headers: readHeaders(req),
		},
		context: { req, signal },
		errorContext: { req, signal },
		errorHandlers: options.errorHandlers,
	},
);
```

`handleHttpRoute` validates declared request segments, flattens or groups them
according to the route, invokes the handler, applies error hooks, validates
declared responses, and returns a normalized `HttpRouteResult`.

`errorContext` is optional. Provide it when error hooks need a different shape
from the handler context.

### Writing the result

Map `HttpRouteResult` to the framework response API with
`handleHttpRouteResult`:

```ts
import { handleHttpRouteResult } from "@rest-rpc/server";

return handleHttpRouteResult(result, {
	setHeader: (name, value) => response.setHeader(name, value),
	sendEmpty: (status) => response.status(status).end(),
	sendJson: (status, body) => response.status(status).json(body),
	sendCustom: (status, body) => response.status(status).send(body),
	sendStream: ({ status, body, contentType, mode }) =>
		writeFrameworkStream({ response, status, body, contentType, mode }),
});
```

The writer handles ordinary headers, content types, and the response-kind header
used by server-first clients. Do not duplicate that logic in each response
branch. A stream writer must also handle backpressure, close the response, and
call the async iterator's `return()` when the client disconnects.

If the framework returns standard Fetch responses, use
`createFetchResponse(result)` from `@rest-rpc/fetch`. For Node
`ServerResponse`, use `writeNodeResponse(result, response)` from
`@rest-rpc/node`.

## Dispatch adapters

### Compile the implementation matcher once

`createHttpDispatcher` accepts both contract-first and server-first nested
implementation trees. Construct it when `createRouteHandler` is called, not for
every request:

```ts
import {
	createHttpDispatcher,
	type DispatchImplementationTree,
	type ImplementationContextArguments,
	type ServerErrorHandlers,
} from "@rest-rpc/server";

type CreateHandlerOptions = {
	bodyParser?: RuntimeBodyParser;
	errorHandlers?: ServerErrorHandlers<Record<string, unknown>>;
};

export function createRouteHandler<
	const TTree extends DispatchImplementationTree,
>(implementations: TTree, options: CreateHandlerOptions = {}) {
	const dispatch = createHttpDispatcher(implementations);

	return async (
		request: RuntimeRequest,
		...contextArguments: ImplementationContextArguments<TTree>
	) => {
		const context = (contextArguments[0] ?? {}) as Record<string, unknown>;
		const target = readRequestTarget(request);

		const result = await dispatch({
			method: target.method,
			path: target.path,
			context,
			signal: requestSignal(request),
			catchParsingErrors: options.bodyParser === undefined,
			errorHandlers: options.errorHandlers,
			decode: async ({ params }) => ({
				params,
				query: readQuery(request),
				headers: readHeaders(request),
				body: await bodyParser(request),
			}),
		});

		if (result === undefined) return { matched: false as const };
		return {
			matched: true as const,
			response: await writeRuntimeResponse(result),
		};
	};
}
```

The dispatcher matches before calling `decode`, excludes WebSocket
implementations, and returns `undefined` when nothing matches. Its matcher sorts
static paths ahead of parameter paths.

The generic `ImplementationContextArguments<TTree>` makes the handler context
argument required only when at least one route requires application context.
The adapter adds `signal` itself, so callers do not pass it.

### When to use the matcher directly

Use `createImplementationMatcher` when the adapter must inspect a match before
dispatch—for example, the Node adapter avoids installing request/response abort
listeners until it knows a route matched. Otherwise prefer
`createHttpDispatcher`, which keeps matching and execution together.

`createRouteMatcher` is for a contract tree. It does not associate matched
routes with implementation handlers and is therefore not the primary helper for
catch-all adapters.

### Parsing failures

Default parsers should normally set `catchParsingErrors: true`; malformed bodies
then become the shared 400 parsing response. If a user supplies a custom parser,
set it to `false` so custom parser exceptions are not silently reinterpreted.

The body parser should only inspect the runtime request. Use its `Content-Type`
header to choose a representation without consulting the matched route or its
contract. Contract validation separately checks the parsed value and enforces a
content type when one was explicitly declared for a custom body.

## Server-first response compatibility

A server-first route without `.response(...)` declarations returns an envelope
such as `{ status, body, contentType? }`. `handleHttpRoute` classifies that
envelope as empty, JSON, NDJSON, custom, or custom-stream output.

The server-first client cannot infer the wire body's representation from HTTP
headers alone. Its server writer must preserve the versioned
`X-Rest-Rpc-Response-Kind` header emitted by `handleHttpRouteResult`. Using the
first-party Fetch/Node response helpers satisfies this requirement. A custom
writer built on `handleHttpRouteResult` does too.

## WebSocket routes

Registration adapters may support WebSockets with the runtime's native upgrade
mechanism:

1. Match the WebSocket implementation.
2. Build query, params, headers, context, and an abort signal.
3. Call `prepareWebSocketUpgrade` before accepting the socket.
4. Return the rejection through the framework if validation or `beforeUpgrade`
   fails.
5. Adapt the accepted socket to `WebSocketLike`.
6. Call `handleWebSocketRoute` with the previously validated request.

Do not pass WebSocket implementations to `handleHttpRoute`; shared HTTP
dispatch deliberately ignores them. The Fetch and Node.js catch-all handlers
currently cover HTTP and SSE only.

## Checklist

- Expose only public, adapter-appropriate builders from your package root.
- Keep framework routing when it provides meaningful middleware or context.
- Use `splitRouteImplementations` for registration adapters.
- Use `createHttpDispatcher` for catch-all HTTP/SSE adapters.
- Decode request data only after a route matches.
- Put `signal` and framework-native values in handler context.
- Use `handleHttpRoute` for validation, execution, normalization, and error hooks.
- Use `handleHttpRouteResult` or the Fetch/Node writer helpers for every result
  kind and server-first response metadata.
- Own backpressure and disconnect cancellation in runtime stream writers.
- Own WebSocket upgrade and lifecycle behavior in the adapter.
