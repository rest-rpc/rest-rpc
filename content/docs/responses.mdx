title: Responses
description: Declare inferred or status-keyed HTTP response shapes.
---

The `response` field declares one successful response body.

```ts
create: {
	method: "POST",
	path: "/todos",
	body: {
		title: z.string().min(1),
	},
	response: todoSchema,
}
```

The status is inferred from the method. `POST` uses `201`; `GET`, `PUT`,
`PATCH`, and `DELETE` use `200` when a body is declared with `response`.

The `responses` field declares response bodies by status code.

```ts
responses: {
	200: todoSchema,
	404: z.object({
		code: z.literal("TODO_NOT_FOUND"),
	}),
}
```

There is no separate `errors` field. Declared non-2xx responses are part of the
route contract.

## Response Bodies

Response body declarations can be Standard Schema-compatible schemas.

```ts
response: z.object({
	id: z.string(),
	title: z.string(),
	completed: z.boolean(),
})
```

`noBody()` marks a status as having no response body.

```ts
import { noBody } from "@rest-rpc/core";

responses: {
	204: noBody(),
}
```

When a route omits both `response` and `responses`, the route has an inferred
no-body response. `DELETE` uses `204`, `POST` uses `201`, and `GET`, `PUT`, and
`PATCH` use `200`.

```ts
remove: {
	method: "DELETE",
	path: "/todos/:id",
}
```

Custom and streaming bodies are covered in advanced docs.

## Response Resolution Rules

Each HTTP route uses exactly one of these shapes:

- `response`: one response body, with status inferred from the method.
- `responses`: an explicit status-keyed response map.
- neither: one inferred no-body response.

A route declaration cannot include both `response` and `responses`.

Status inference:

- `response` with `POST` becomes `201`.
- `response` with `GET`, `PUT`, `PATCH`, or `DELETE` becomes `200`.
- omitted responses with `DELETE` become `204`.
- omitted responses with `POST` become `201`.
- omitted responses with `GET`, `PUT`, or `PATCH` become `200`.

`commonResponses` are merged into the resolved route responses. Route statuses
override common statuses. An explicit empty `responses: {}` resolves from
`commonResponses`.

## Handler Returns

If a route has exactly one successful response and that response has no declared
headers, the handler can return the success body directly.

```ts
return {
	id: "todo_1",
	title: "Write docs",
	completed: false,
};
```

Handlers can always return an explicit response envelope.

```ts
return {
	status: 404,
	body: {
		code: "TODO_NOT_FOUND",
	},
};
```

The direct body shortcut is only valid when the success status is unambiguous and
the response does not need declared `responseHeaders`.

## Explicit Success

An explicit response envelope includes the status in the handler result.

```ts
create({ title }) {
	return {
		status: 201,
		body: createTodo({ title }),
	};
}
```

## Declared Error Responses

Declared non-2xx responses need an explicit envelope.

```ts
get({ id }) {
	const todo = todos.get(id);

	if (!todo) {
		return {
			status: 404,
			body: {
				code: "TODO_NOT_FOUND",
			},
		};
	}

	return todo;
}
```

You can also use `ContractResponseError` to throw a declared error response when that's more convenient.

```ts
throw new ContractResponseError(api.todos.get, {
	status: 404,
	body: {
		code: "TODO_NOT_FOUND",
	},
});
```

## Client Responses

Every HTTP route exposes `fetchResponse()`.

```ts
const response = await api.todos.get.fetchResponse({
	id: "todo_1",
});
```

It returns declared responses as values.

```ts
if (response.declared && response.status === 200) {
	response.body;
}

if (response.declared && response.status === 404) {
	response.body.code;
}
```

It also exposes undeclared responses.

```ts
if (!response.declared) {
	throw new Error(`Unexpected response: ${response.status}`);
}
```

Routes with one successful response also expose `fetch()`.

```ts
const todo = await api.todos.get.fetch({ id: "todo_1" });
```

`fetch()` returns the successful response body directly. It throws when the
response is undeclared or is not a declared success response.
