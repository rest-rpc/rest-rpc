---
title: Plain-Output Routes
description: Use flat inputs and plain results with derived or explicit HTTP methods and paths.
---

A route does not have to choose between a function-shaped API and an explicit
HTTP interface. Choose the method and path, the input form, and the output form
independently.

Without a method setter, the route uses POST and derives its path from the
contract tree. `.input(schema)` declares one flat value, sent as a body on POST,
PUT, PATCH, and DELETE. `.output(schema)` declares one successful result that
the client returns directly.

```ts
const api = {
	todos: {
		create: route.input(z.object({ title: z.string() })).output(todoSchema),
	},
};

const todo = await client.todos.create({ title: "Write docs" });
```

The route above uses `POST /todos/create`. Renaming a tree key changes the
derived URL. Client and server deployments should treat those keys as part of
their wire contract.

## Choose a Method and Path

An explicit method setter works with the same flat input and plain output:

```ts
const api = {
	todos: {
		search: route
			.get("/todos/search")
			.input(z.object({ term: z.string() }))
			.output(z.array(todoSchema)),
		create: route
			.post("/todos")
			.input(z.object({ title: z.string() }))
			.output(todoSchema),
	},
};

await client.todos.search({ term: "open" });
await client.todos.create({ title: "Write docs" });
```

A flat GET input is encoded as query parameters and must satisfy the same
scalar-or-array wire constraints as `.query()`. A flat input requires a static
path. Use `.params()` and the segmented request form for paths containing
`:id` or `{id}`.

## Choose Request Segments

Use `.query()`, `.params()`, `.body()`, and `.headers()` when the request
has distinct HTTP segments. Choosing any segment closes `.input()`. Plain
`.output()` remains available with segmented input.

```ts
const getTodo = route
	.get("/todos/:id")
	.params(z.object({ id: z.string() }))
	.output(todoSchema);

const todo = await client.todos.get({ params: { id: "todo_1" } });
```

GET routes cannot declare a body.

## Choose Status Responses

Use `.response(status, schema)` when the client or handler needs status
envelopes. It can be repeated for different statuses and closes `.output()`.
This choice is independent of the method and input form.

```ts
const createTodo = route
	.input(z.object({ title: z.string() }))
	.response(201, todoSchema)
	.response(409, z.object({ code: z.literal("CONFLICT") }));
```

The client receives a status-discriminated response, while a route declared
with `.output()` returns the decoded value directly.

## Server-First Inference

Attach `.handler()` to a server route when the output is inferred from the
handler. If every possible awaited return has a top-level `status`, rest-rpc
infers response envelopes. If none has `status`, it infers a plain output. A
return union mixing those two forms is invalid.

```ts
const list = route.get("/todos").handler(() => listTodos());
const created = route.post("/todos").handler(() => ({
	status: 201,
	body: createTodo(),
}));
```

A plain value uses JSON by default. An `AsyncIterable` infers a stream.
`{ contentType, data }` infers a custom-content plain output.

```ts
const report = route.handler(() => ({
	contentType: "text/plain" as const,
	data: createTodoReport(),
}));

const events = route.handler(() => streamTodoEvents());
```

Use `.output(schema)` or `.streamOutput(schema)` when output validation or a
stable schema is needed. For a custom declared output, the handler returns
`{ contentType, data }`; a declared stream handler returns an async iterable.
`.response(status, schema)` and `.streamResponse(status, schema)` constrain
status-envelope handlers.

Request and response setters may appear in either order. `.metadata()` and
`.openAPI()` can appear anywhere before `.handler()`.
