A contract is a plain TypeScript object composed from route builders.

```ts
import { route } from "@rest-rpc/core";
import { z } from "zod";

const todoSchema = z.object({
	id: z.string(),
	title: z.string(),
	completed: z.boolean(),
});

export const api = {
	todos: {
		get: route.get("/todos/:id").response(200, todoSchema),
	},
};
```

The contract is used at runtime and at type level. It can drive server handlers,
clients, TanStack Query options, and OpenAPI generation.

## Route Builders

Start a route with an HTTP method and path, then add request and response
declarations with chainable setters. Body, query, and path-parameter setters
each receive one schema. Headers are the exception: `.headers()` receives a
`Record<string, schema>` because each header has its own name.

Use `.response(status, schema)` repeatedly for declared statuses. Protocol
routes start with `.sse(path)` or `.ws(path)` and have their own completion
setters.

## Request Model

Request data is declared by HTTP location on the route builder.

```ts
route
	.patch("/todos/:id")
	.params(z.object({ id: z.string() }))
	.query(z.object({ includeCompleted: z.coerce.boolean().optional() }))
	.headers({ "x-request-id": z.string().optional() })
	.body(z.object({ title: z.string() }))
	.response(200, todoSchema);
```

Those locations remain part of the contract. By default, clients and server
handlers receive one flattened request object.

```ts
await client.todos.update.fetch({
	id: "todo_1",
	includeCompleted: true,
	"x-request-id": "req_1",
	title: "Write docs",
});
```

```ts
const routes = router(api, {
	todos: {
		update({ id, includeCompleted, title, "x-request-id": requestId }) {
			return updateTodo({ id, includeCompleted, title, requestId });
		},
	},
});
```

The flattened shape is only the default TypeScript and adapter API. `rest-rpc`
still serializes each value to the HTTP location where it was declared.

Create a route factory with `route.with({ flattenRequestKeys: false })` when you
want clients and handlers to receive explicit HTTP request segments.

```ts
const groupedRoute = route.with({ flattenRequestKeys: false });

export const api = {
	todos: {
		update: groupedRoute
			.patch("/todos/:id")
			.params(z.object({ id: z.string() }))
			.query(z.object({ includeCompleted: z.boolean().optional() }))
			.body(z.object({ title: z.string() }))
			.response(200, todoSchema),
	},
};
```

```ts
await client.todos.update.fetch({
	params: { id: "todo_1" },
	query: { includeCompleted: true },
	body: { title: "Write docs" },
});
```

```ts
const routes = router(api, {
	todos: {
		update({ params, query, body }) {
			return updateTodo({
				id: params.id,
				includeCompleted: query.includeCompleted,
				title: body.title,
			});
		},
	},
});
```

See [Shorthand vs Explicit](/docs/shorthand-vs-explicit/) for the broader
design tradeoff.

## Path Params

Full dynamic path segments infer string path params. In this route, `:id`
contributes an `id: string` input:

```ts
route.get("/todos/:id").response(200, todoSchema);
```

Explicit `params` replace the inferred string schema for the same params.

```ts
route
	.get("/todos/:id")
	.params(z.object({ id: z.string().uuid() }))
	.response(200, todoSchema);
```

Path parameter rules:

- Only full path segments are params: `:id` and `{id}` are params.
- Partial segments are static: `/files/file-{id}` and `/todos/:id.json` do not declare params.
- Inferred params are string schemas.
- Explicit `params` must match the path params exactly.
- `pathPrefix` must be static and cannot include path params.

## Flattened Key Collisions

:::note
This section only applies when flattened request keys are enabled. With
`flattenRequestKeys: false`, request fields stay under their explicit HTTP
segments, so flattened key collisions do not apply.
:::

Every flattened request key must identify exactly one HTTP location. A route is
invalid when the same key appears in multiple request locations.

```ts
route
	.post("/todos")
	.params(z.object({ id: z.string() }))
	.body(z.object({ id: z.string() }))
	.response(201, todoSchema);
```

Both fields would flatten to `id`, so the route builder rejects the contract.

Other request key constraints:

- `context` is reserved for the server handler context.
- Header keys are checked case-insensitively, so `authorization` and `Authorization` collide.
- Explicit path params in the URL must have matching `params` schema keys.
- Explicit `params` schema keys must correspond to actual path params.

## JSON Query

`jsonQuery()` declares a JSON-shaped query value.

```ts
import { jsonQuery, route } from "@rest-rpc/core";

const api = {
	search: route
		.get("/search")
		.query(
			jsonQuery(
				z.object({
					page: z.number(),
					includeArchived: z.boolean(),
					filters: z.object({
						tags: z.array(z.string()),
					}),
				}),
			),
		)
		.response(200, z.object({ results: z.array(z.string()) })),
};
```

The client and handler use a top-level `query` value:

```ts
await client.search.fetch({
	query: {
		page: 2,
		includeArchived: false,
		filters: { tags: ["docs", "api"] },
	},
});
```

`rest-rpc` transports that value in the URL query parameter named `query`,
parses it on the server, and validates it with the wrapped schema.

## Responses

`.response(status, schema)` declares a response body for a status.

```ts
route
	.post("/todos")
	.body(z.object({ title: z.string().min(1) }))
	.response(201, todoSchema);
```

`rest-rpc` assigns the status from the HTTP method: `POST` uses `201`, and other
methods use `200`.

Call `.response()` once for each declared status code.

```ts
route
	.get("/todos/:id")
	.response(200, todoSchema)
	.response(404, z.object({ code: z.literal("TODO_NOT_FOUND") }));
```

Non-2xx statuses are declared the same way as 2xx statuses.

Routes with no `response` or `responses` default to a no-body response. `DELETE`
uses `204`, `POST` uses `201`, and other methods use `200`.

Status-specific response headers can be declared by passing an object containing
`body` and `headers` as the response schema.

```ts
route
	.post("/todos")
	.body(z.object({ title: z.string().min(1) }))
	.response(201, {
		body: todoSchema,
		headers: {
			location: z.string(),
			"x-next-cursor": z.string().optional(),
		},
	});
```

## Shared Route Options

`route.with()` creates a route factory with shared options for every route built
from it. The option names match the builder setters: `headers`, `responses`,
`metadata`, `openApi`, and `pathPrefix`.

```ts
const apiRoute = route.with({
	pathPrefix: "/api",
	metadata: { auth: "required" },
	headers: { "x-request-id": z.string().optional() },
	responses: { 401: z.object({ code: z.literal("UNAUTHORIZED") }) },
	openApi: {
		tags: ["Todos"],
		security: [{ bearerAuth: [] }],
	},
});

export const api = {
	todos: {
		list: apiRoute
			.get("/todos")
			.withOpenApi({ summary: "List todos" })
			.response(200, z.object({ items: z.array(todoSchema) })),
	},
};
```

The route above is normalized to `GET /api/todos`, includes the factory header,
the factory `401` response, and keeps the route-specific OpenAPI summary.

## Single Routes

`route()` declares one route.

```ts
import { route } from "@rest-rpc/core";

export const getTodo = route.get("/todos/:id").response(200, todoSchema);
```
